# Continuing StreamTube with AI - Phase 03: Video Upload and Processing

## Description

**StreamTube** is the video sharing platform you saw being built throughout the
course. The instructor delivered **Phase 01 (base setup)** and **Phase 02
(authentication, users, and channels)**, backend and frontend, following the
AI-driven development workflow used in the course.

Your challenge is to **continue the project by fully implementing the next
phase in the sequence, Phase 03 - Video Upload and Processing**. Unlike a
simple CRUD feature, Phase 03 is an engineering challenge on its own: it
involves **large file storage, asynchronous queue-based processing, a video
worker, streaming, and new Docker infrastructure**. You will drive all of this
using AI as the main tool, following the project workflow end to end.

This is a **backend** challenge: the delivery is the API, the worker, the
infrastructure, and the process artifacts. (There is a frontend in the
repository, but the video interface is not part of this phase.)

## AI Tooling

The base project is built for **Claude Code**, which is the **recommended**
tool: the AI foundation (skills, sub-agents, `CLAUDE.md`, rules, and
`.mcp.json`) is already prepared for it.

You **can** use another agentic tool if you prefer (Gemini CLI, OpenAI Codex,
and similar). But note: the repository's AI foundation is specific to Claude
Code. If you choose another tool, **it is your responsibility to port that
foundation to its convention** before starting:

* `CLAUDE.md` -> the equivalent instruction file (for example, `GEMINI.md` in
	Gemini CLI, `AGENTS.md` in Codex).

	(commands, extensions, custom modes) or, if there is no equivalent, perform
	the same workflow manually.
* `.mcp.json` and the MCP servers (Postgres, context7) -> the MCP configuration
	of the chosen tool.

Always consult the official documentation for the correct file, folder, and

the **delivered artifacts are the same** (described below): only the machine

## Phase 03 scope - Video Upload and Processing

You will deliver the following capabilities (full definition in
`docs/project-plan.md`, Phase 03):

* **Object storage** for video files and thumbnails.
* **Background processing queue** and a **worker** that consumes it.
* **Video upload up to 10GB without blocking the system** (do not hold the API
	during the upload).
* **Automatic draft pre-registration** when the upload starts.
* **Automatic processing after upload**: duration and metadata extraction.
* **Automatic thumbnail generation** from a video frame.
* **Unique URL per video**, with no conflict with others.
* **Streaming playback** (without requiring a full download).
* **Video download** by the user.

**Original deliverables:** working upload up to 10GB, automatic video
processing, working streaming, and generated unique URLs.

**Persistence:** a video entity/table linked to the channel, with at least
identification, owner (channel), title, **status** (e.g. draft -> processing
-> ready/error), storage keys for the file and thumbnail, duration and
metadata, and the unique URL identifier. The exact model is defined in the
plan (Data Model).

**Decisions you need to make and justify in research:**

* The **queue technology** - the project plan leaves it explicitly open
	("TBD"). This is the main stack decision for the phase.
* The **strategy for uploading 10GB without blocking** (e.g. direct upload to
	storage via pre-signed URL / multipart, instead of passing the file through
	the API).
* How the **worker** runs (separate process/container) and how it extracts
	metadata and generates the thumbnail (FFmpeg/ffprobe).
* The **unique URL** strategy and the **streaming** strategy (e.g. range
	requests / `206 Partial Content`).
* The video **status lifecycle** and what happens if processing fails.

**About object storage:** it is not an open choice. The project already points
to **S3-compatible** storage - in practice you run **MinIO** locally in Docker
(same S3 API) and would switch to S3 in production. What you decide here is
*how* to use it (bucket/key organization, pre-signed upload), not *which*
storage to use. The genuinely open stack decision is the **queue**.

These decisions are the heart of the research stage. Research the options,
record the trade-offs, and write the choice in the decisions document, and only
then move on to planning.
